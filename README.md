## 三项任务交付清单

### Task01：游戏策划案与 AI 协作记录

小游戏开发方向的策划案至少覆盖：

- 游戏概述：游戏名称、核心概念、游戏类型、目标受众、视觉风格；
- 核心玩法：核心循环、操作机制、核心规则；
- 系统设计：角色系统、经济与数值系统、背包与道具系统；
- 游戏世界与剧情：故事发生时间、地点和背景；
- 可视化表达：UI 线框图、页面结构图、核心玩法流程图；
- AI 协作记录：AIGC 工具、初始想法、人机互动流程、提示词和产出数据。

最终文件按以下格式命名：

```text
Track01_Task01_<队伍ID后五位>_<作品名称>_游戏策划案.pdf
Track01_Task01_<队伍ID后五位>_<作品名称>_游戏策划案.docx
Track01_Task01_<队伍ID后五位>_<作品名称>_AI协作记录.pdf
Track01_Task01_<队伍ID后五位>_<作品名称>_AI协作记录.docx
```

文档排版要求：封面包含作品名称、队伍 ID、日期；标题使用黑体三号加粗；正文使用宋体小四、1.5 倍行距；关键词使用蓝色高亮并附脚注解释；页边距为标准 2.54 cm；字数不限，但应完整阐述任务要求的必要内容。

### Task02：游戏素材图、主场景图与 AI 协作记录

小游戏开发方向应提交游戏所需的全部美术素材，包括道具、角色、场景、动画帧等，并至少包含核心场景（如游戏开始界面、关卡选择界面、游戏世界界面）。

- 保留 AI 生成过程、提示词、筛选和修改记录。

文档类成果沿用 Task01 的排版规范。

最终文件或文件夹按以下格式命名：

```text

Track01_Task02_<队伍ID后五位>_<作品名称>_主场景图
```

### Task03：核心可玩实体、运行逻辑说明、测试与迭代记录、交互演示视频

提交可体验的游戏应用程序及源码。无需完整商业化游戏，但必须包含核心循环，例如一个完整关卡设计或 3 分钟以上的可体验内容。还应提交：

## 本项目工程约定

以下内容是仓库内部的代码风格和协作约定，不是 PDF 的原文要求；目的是让初始应用便于继续开发、评审和打包。

### 目录职责

建议将可运行项目放在 `Task03/Original/`，最终可直接运行的源码、构建产物和必要资源放在 `Task03/Final/`。策划和素材的原始过程分别放在 `Task01/Original/`、`Task02/Original/`，提交版本放在对应的 `Final/`。

```text
Task03/Final/<项目名>/
├─ src/            # 游戏逻辑、场景和 UI
├─ assets/         # 运行时使用的图片、音频、字体
├─ tests/          # 可自动化的规则和数值测试
├─ docs/           # 面向开发者的补充说明
├─ README.md       # 独立运行说明（若项目需要）
└─ <项目配置文件>  # 由所选引擎或框架生成
```

### 命名与代码风格

- 源码内部文件夹使用 `kebab-case`，代码文件使用项目语言的常见命名规范；官方提交目录和成果文件严格使用赛题规定的中文与下划线格式。
- 类型、类、组件使用 `PascalCase`；函数、变量和资源 ID 使用 `camelCase`；常量使用 `UPPER_SNAKE_CASE`。
- 一个模块只承担一个清晰职责；输入、状态更新、渲染和结算逻辑分层，避免把整局游戏写进单个巨型脚本。
- 游戏规则使用数据驱动：关卡、道具、数值和文本优先放在可审阅的数据文件中，代码只处理通用逻辑。
- 公共函数注明输入、输出和副作用；复杂规则前写简短注释，注释解释“为什么”，不重复代码表面行为。
- 保持格式化、静态检查和测试命令可重复执行；提交前清理临时导出、缓存、密钥和本机路径。
- AI 生成或修改的代码必须经过人工审阅、运行验证和版权检查，并在 AI 协作记录中保留工具、提示词、版本和修改说明。
